# Workshop lead notes

Attendees use [START-HERE.md](../START-HERE.md); this file is your delivery view.

## Before the event

- Choose the 60/90/120-minute agenda in the root README and announce the actual output.
- Check every device/environment, pre-download large assets, and prepare a clearly labeled fallback.
- Rehearse the learner starter path as well as the completed reference.
- Decide pair roles: driver edits, navigator predicts and checks. Switch after the main build.
- Keep {{REFERENCE_RESULTS_AND_TROUBLESHOOTING_LOCATION}} ready.

## Delivery prompts

| Moment | Ask | Look for |
|---|---|---|
| Opening | “Where would you use the app we are building?” | A familiar problem, not product vocabulary |
| Lab 1 | “Which component produced this result?” | Correct technology/runtime/model distinction |
| Lab 2 | “Predict the effect before you change it.” | Reasoning before execution |
| Lab 3 | “What else could explain this result?” | Controls, failure diagnosis, uncertainty |
| Lab 4 | “Which part would you adapt for your own work?” | Transfer beyond the supplied example |
| Close | “Show one result and one limitation.” | Evidence rather than an unchecked success claim |

## Hints and recovery

After five stuck minutes, reveal hint 1: the conceptual decomposition. Hint 2 names the relevant API or intermediate value. Reveal the solution only after an attempt and ask the learner to explain it. The topic-specific answer key is {{ANSWER_KEY_LOCATION}}.

If setup fails, use a prepared pair or an explicitly labeled recorded result. If behind schedule, omit Lab 4 or reduce repeat measurements; preserve the implementation and reflection. Never silently switch to reference code and count it as learner completion.

## Simple assessment

One point each: explains where the technology fits; executes a real path; implements a change; tests a new case; explains a limitation. Collect the worksheet plus a 60–90 second demo. This is workshop feedback, not vendor certification.
